## このファイルは何か

サイトマップ(`/{リポジトリ名}/sitemap`)の、**横断する判断の記録**。
図そのもののデータは隣の `sitemap.json` が一次資料で、箱・線それぞれの説明もその中にある。
見せ方の決まり(寸法・余白・文字の大きさ・リンクの作り方)は Web アプリ側のコード `apps/web/src/lib/sitemap.ts` と `apps/web/src/app/tabs/sitemap/` が一次資料。

元は `apps/web/src/data/sitemap.ts` のコメントだったものを、#588(#543 の最終段)でここへ移した。

## この図が表していること・表していないこと

**表していること。**
アプリ(ネイティブアプリ / Webアプリ)と、その中のページ、ページの中のタブという入れ子。
ページからページへの遷移(結線)。
各画面のパスと、画面が何をするかの一文、関連する WBS の項目。

**表していないこと。**
画面の中のレイアウト(どこに何が並ぶか)は表さない。
それは各サイトの詳細ページ(`/{リポジトリ名}/sitemap/sites/{id}`)のワイヤーフレームで見る。
画面に出るデータの構造は TM(`/{リポジトリ名}/tm`)、クラスの構造は Classes(`/{リポジトリ名}/class-diagram`)、システムの配置はポンチ絵(`/{リポジトリ名}/unchi`)と構成図(`/{リポジトリ名}/deployment-diagram`)が持つ。
権限・ログイン状態による出し分けも表していない(今のところ、どちらのアプリにもログインの概念が無い)。

## ID の割り当て

- `1` = ルート
- `2`-`3` = アプリ
- `4`-`18` = ネイティブアプリ(ページとタブ)
- `19`-`49` = Webアプリのページ
- `50`- = Webアプリの、メニューに出ないページ

結線の ID。

- `100`- = ネイティブアプリ側
- `130`- = Webアプリのページ
- `150`- = Webアプリの、メニューに出ないページ

### ID を明示で書く理由(#588)

以前は Webアプリのページの ID を `apps/web/src/data/navigation.ts`(左メニュー)の並びから自動採番していた(`19 + 並び順`)。
メニューと自動で同期させるためだったが、#548 でポンチ絵がメニューに増えたときに、**新しい ID のノードが黙って生まれた**。
位置が記録されていない箱が1つでき、それが何なのかを突き止めるのに手間がかかった(#577)。

仕様データがリポジトリの外(`yyz/spec/`)に出ると、Web アプリの `navigation.ts` とは同期できない。
それ抜きでも、黙って箱が増えない形のほうが良いので、**ID は JSON に明示で書く**。

ID は変えてはいけない。
位置の手調整(`apps/web/src/data/layout/sitemap.json`)とワイヤーフレーム(`apps/web/src/data/wireframes/<id>.ts`)が ID をキーにしているため、振り直すと手調整が迷子になる。

## ページの中のタブを、別のノードにしない

タブ切り替えはパスが変わらず、クエリパラメータが変わるだけ(別ページへの遷移ではない)。
そのため、矢印で繋ぐ別ノードにはせず、**ページのノードの入れ子(`children`)として内側に描く**。

d3.sitemap の `fitting()` は `children` の位置を「親からの相対座標」として親の絶対座標に加算し、親の大きさも `children` を包含するよう自動で広げる。
そのため JSON には相対座標だけを書けばよい。

`children` の位置は「**親の左上**」からの相対座標で書く(位置の手調整 `layout/sitemap.json` と同じ座標系)。
タブを持つページには内側の余白を付け、右端・下端にも余白が出るようにする(d3.sitemap 0.6.0 の `padding`)。
d3.sitemap は余白の内側を起点にするので、描画に渡すときに余白の分を引く(`apps/web/src/app/tabs/sitemap/renderNodes.ts`)。
**保存値の座標系は変えない。**
変えると、開いたままの画面が古い座標系の値を書き戻して配置がずれる。

## 位置は JSON、寸法と余白はコード

**位置(`position`)は JSON に持つ。**
どこに置くかは図を描いた人が決めたことで、計算では出せない。

**寸法と余白はコードの決まりとして持つ**(`apps/web/src/lib/sitemap.ts`)。
箱の大きさは「ページは一律、ページの中のタブは一律」という見せ方の決まりなので、1件ずつ JSON に書き写さない。
入れ子を持つノードの余白も同じ理由でコードに置く。

図の上での位置の手調整(ドラッグ・インスペクタ)と視点(パン / ズーム)は、**JSON には書き戻さない**。
`apps/web/src/data/layout/sitemap.json` に別途保存する(#588 では移さない。保存 API が Web アプリ配下に書く作りのため)。

## 箱の幅を1つの定数に揃えた経緯(#588)

パスは箱の上に添えて描く。
箱より長いパスはみ出すため、かつては **URL ごとに幅を分岐**させていた。
#548 で構成図の URL が `/yaoyorozu/deployment-diagram` に変わって既定幅からはみ出し、#549 でその1つだけを +80 広げる対症療法を入れていた。

#588 で、**パスを添える箱は同じ幅**に統一した(定数1つ)。
URL ごとの分岐を無くす方針は 2026-10-05 に合意し、#543 の最終段で行う持ち越しにしていた。
基準は「いちばん長いパス表示が収まる幅」。
収まっているかは `npm run web:check-diagram -- sitemap` の「枠からのはみ出し」が 0 件であることで担保する。

ページの中のタブの幅も同じ考え方で、「いちばん長いタブ名(`settings.local.json` に別タブの印が付いたもの)が収まる幅」にしている。

## ノードの名前とパスの見せ方

ページのノードの名前は**画面の名前**にする(ネイティブアプリのウィンドウのタイトル・ドックの表示に合わせる)。
パスは名前の代わりにはせず、**箱の上に添える**。

名前はそのサイトの詳細ページへのリンクにし、パスは**ブラウザで開けるものだけ**その画面へのリンクにする。

ブラウザで開けるかは、アプリのノードに付けた `browsable` の印で決める。
Webアプリの画面のパスはそのまま URL だが、ネイティブアプリの画面のパス(`/settings` など)はアプリ内部の経路で、ブラウザでは開けない。
この違いは見せ方ではなくデータなので、JSON 側に持たせている(印はアプリのノードに1つ付け、その配下が受け継ぐ)。
引数を含むパス(`/{リポジトリ名}/sitemap/sites/:id` など)は、どの値を入れるべきか決められないのでリンクにしない。

d3.sitemap 0.6.0 のリンクは必ず別タブで開くため、基本デザイン「リンクテキスト」の「新しいタブで開くことを予告する」に従って `↗` を添える(SVG の文字の中にはアイコンを置けないため、`uiIcon.ts` の external-link の代わり)。

## 説明と関連する WBS の出典

各ノードの説明(`description`)は、**各画面の実装から書き起こしたもの**(`apps/native/react/src/pages/*`・`apps/web/src/app/tabs/*`)。

関連する WBS(`wbsIds`)は、その画面・アプリに対応する WBS の項目(`yyz/spec/wbs.json`)。
対応する項目が無いもの(ネイティブアプリの各画面など)は**空にする**。
推測で割り当てない。

## 「サイトの詳細」ノードの置き方

`50`(サイトの詳細)はメニューに出ないページで、位置を JSON に直接書いている。
手調整後の配置では Webアプリのページが x≈-1300 に縦に並び、結線は Webアプリの左(90)から出て各ページの右(270)へ入る。
そこへ馴染むよう、サイトマップのページの左隣(同じ高さ)に置き、結線も同じ向きにする。
